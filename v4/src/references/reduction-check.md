# Reduction Check — 饱和度评分框架

Mode 6 (Reduction Check) 帮助用户检测迭代过程中累积的不必要复杂度。核心理念：**过饱和不是"细节太多"，而是"偏离第一性原理"**。如果设计细节直接服务于第一性原理，再多也不嫌多；如果设计细节是在"修复其他设计细节引发的问题"，那就是过饱和。

## Step 1: 锚定第一性原理 {#step-1-anchor}

评估之前必须先锚定项目的第一性原理。没有锚点的评分等于没有坐标系的测量。

### 锚定模板

```
项目第一性原理锚点：
├── 核心问题：这个项目要解决什么根本问题？（一句话）
├── 核心用户：谁是第一优先级使用者？（一个角色）
├── 核心约束：如果只能保留一个规则，保留哪个？（一条规则）
└── 成功标准：怎样算"成了"？（一句话）
```

### 锚定质量检查

| 检查项 | 通过标准 | 不通过信号 |
|--------|----------|-----------|
| 核心问题 | 一句话说完，无从句 | 包含"并且"、"同时"、"以及" |
| 核心用户 | 一个具体角色 | "所有人"、"各类用户" |
| 核心约束 | 可以直接判断一个设计决定的对错 | 太抽象，无法用于决策 |
| 成功标准 | 可以在30秒内检验 | 需要复杂评估流程才能判断 |

**如果用户无法用一句话说清每一项，这本身就是过饱和的信号。** 此时 Coach 应先协助提炼第一性原理，再进行评分。

## Step 2: 逐元素饱和度评分 {#step-2-element-scoring}

对产出物中每个可识别的"设计元素"进行评分。设计元素包括：一个概念、一条规则、一个层级、一个流程步骤、一个评分维度、一个分类体系等。

### 2a. 距离层级（Distance Tier）

用树状模型判断每个元素离第一性原理的距离：

| 层级 | 定义 | 基础分 | 判断标准 |
|------|------|--------|----------|
| **L0 根** | 第一性原理本身 | 0 | 不参与评分，是锚点 |
| **L1 主干** | 直接实现第一性原理的核心机制 | +1 | 删掉则系统崩溃，不可替代 |
| **L2 枝干** | 为核心机制服务的配套设计 | +2 | 重要但可替代，有其他实现方式 |
| **L3 叶片** | 具体操作规则、示例、例外处理 | +4 | 锦上添花，删掉不影响核心功能 |
| **L4 寄生** | 为修复其他设计元素的缺陷而存在 | +8 | 过饱和直接证据 |

**层级判断问法：**
- L1 测试："如果删掉这个元素，系统还能运转吗？" → 不能 = L1
- L2 测试："能用更简单的方式实现同样的目的吗？" → 能 = L2
- L3 测试："这是核心功能还是辅助说明？" → 辅助 = L3
- L4 测试："这个元素是为了解决另一个设计元素引发的问题吗？" → 是 = L4

### 2b. 惩罚因子（加分 = 更饱和 = 更危险）

| 因子 | 条件 | 惩罚值 | 解释 |
|------|------|--------|------|
| **P1 循环依赖** | 与另一个非L1元素互相依赖 | +3 | 设计产生了自我引用的复杂度 |
| **P2 专有术语** | 引入了需要额外解释的新概念 | +2 | 每个新概念是读者的认知负担 |
| **P3 例外处理** | 是某条规则的例外情况 | +2 | 例外越多，规则越脆弱 |
| **P4 嵌套条件** | 包含"如果...但如果...除非..." | +3 | 嵌套条件是复杂度的最可靠指标 |
| **P5 解释成本** | 需要超过2句话向新人解释 | +1 | 如果解释不清，可能不该存在 |
| **P6 孤岛元素** | 与系统中其他部分没有明确关联 | +2 | 可能是迭代残留，忘记删除 |

### 2c. 奖励因子（减分 = 更简约 = 更健康）

| 因子 | 条件 | 奖励值 | 解释 |
|------|------|--------|------|
| **B1 直觉可用** | 不需要查文档就能理解和使用 | -2 | 简单到不需要说明书 |
| **B2 即时可验** | 可以在30秒内检验是否生效 | -2 | 短反馈循环 = 高实用性 |
| **B3 单一职责** | 只做一件事，做得很清楚 | -1 | 职责清晰 = 低耦合 |
| **B4 可删除性** | 删除后系统仍运转，只是稍弱 | -1 | 优雅退化 = 设计健壮 |
| **B5 复用性** | 在多个场景中被引用 | -1 | 被多次引用说明确有价值 |

### 2d. 单元素得分公式

```
元素饱和度 = 距离层级基础分 + Σ(惩罚因子) - Σ(奖励因子)
```

得分下限为 0（不会出现负分）。

| 得分范围 | 状态 | 含义 |
|----------|------|------|
| ≤ 2 | 🟢 健康 | 有充分存在理由 |
| 3-5 | 🟡 注意 | 需审视是否值得保留 |
| 6-8 | 🟠 警告 | 强烈建议简化或删除 |
| ≥ 9 | 🔴 过饱和 | 应立即删除或彻底重构 |

## Step 3: 系统级饱和度诊断 {#step-3-system-diagnosis}

逐元素评分后，汇总为三个系统级指标。

### 3a. 饱和度分布图

统计四个状态区间的元素数量和占比，可视化呈现：

```
🟢 健康 (≤2)：  ████████████  12个 (48%)
🟡 注意 (3-5)：  ██████       6个  (24%)
🟠 警告 (6-8)：  ████         4个  (16%)
🔴 过饱和 (≥9)：██           3个  (12%)
```

### 3b. 饱和度指数（Saturation Index）

```
饱和度指数 = (🟠警告数 × 2 + 🔴过饱和数 × 5) / 总元素数 × 100
```

| 指数范围 | 状态 | 建议行动 |
|----------|------|----------|
| 0-15 | ✅ 精简 | 系统健康，继续迭代 |
| 16-30 | ⚠️ 轻度膨胀 | 下一轮迭代中安排一次收缩（T07） |
| 31-50 | 🔶 中度过饱和 | 暂停新增功能，专门做一轮精简迭代 |
| 51-75 | 🔴 重度过饱和 | 回到第一性原理，用 T01 重写核心框架 |
| >75 | ⛔ 系统性危机 | 建议 T08 版本跳跃 — 从零重建 |

### 3c. 层级分布健康度

健康系统的层级分布呈金字塔形：

```
理想分布：
L1 ████ (20-30%)     ← 核心机制占比适中
L2 ██████ (30-40%)   ← 支撑设计是最大层
L3 ████ (20-30%)     ← 细节适量
L4 █ (0-10%)         ← 补丁设计极少
```

**层级健康度公式：**

用一个加权分数替代多条件判断，直接输出层级健康状态：

```
层级健康度 = L1占比×1 + L2占比×0.5 - L3占比×0.3 - L4占比×2
```

| 健康度范围 | 状态 | 含义 |
|-----------|------|------|
| > 0.15 | ✅ 金字塔健康 | 核心+支撑占主导 |
| 0 ~ 0.15 | ⚠️ 轻度头重脚轻 | L3/L4 开始挤压核心 |
| < 0 | 🔴 倒金字塔 | 细节和补丁压过核心结构，需要结构性精简 |

示例：L1=23%, L2=33%, L3=37%, L4=7% → 0.23×1 + 0.33×0.5 - 0.37×0.3 - 0.07×2 = 0.23 + 0.165 - 0.111 - 0.14 = **0.144**（⚠️ 轻度头重脚轻——与直觉一致）

## Step 4: 处方与行动 {#step-4-prescription}

对 🟠 和 🔴 元素给出具体处置建议。

### 4a. 四种处置方式

| 处置 | 适用场景 | 操作 |
|------|----------|------|
| **删除** | 元素不需要存在 | 直接移除，确认系统仍运转 |
| **合并** | 两个元素功能重叠 | 合为一个，消除冗余 |
| **降级** | 元素有微弱价值但不值得作为规则 | 从"规则"变为"建议"或"附注" |
| **重构** | 元素有价值但实现方式过于复杂 | 保留目的，用更简单的方式实现 |

### 4b. L4 寄生元素的特殊处理

对 L4 元素，核心行动不是删除 L4 本身，而是：
1. **追溯上游**：它在修复哪个 L2/L3 元素的什么缺陷？
2. **修复源头**：修复上游缺陷使 L4 不再需要
3. **移除 L4**：上游修复后，L4 自然消失

### 4c. 处方验证

精简后可以再跑一次 Reduction Check，形成闭环：
```
检查 → 精简 → 再检查 → 确认饱和度下降
```

| 场景 | Reduction Check 的角色 | 推荐搭配 |

## 元评估声明

当 Reduction Check 被用于评估**包含 Reduction Check 框架自身**的产出物时（即自诊断），存在不可避免的循环引用：惩罚因子 P1-P6 和奖励因子 B1-B5 会成为被评估的对象，同时又是评估工具本身。

**处理规则：**
- 对框架自身的评分组件（距离层级定义、惩罚因子、奖励因子、饱和度公式），标注为 **「元评估」** 而非常规评估
- 元评估元素的得分不纳入饱和度指数计算，单独列示供参考
- 元评估的判断标准：该评分组件是否能被更简单的机制替代且不损失评估精度
