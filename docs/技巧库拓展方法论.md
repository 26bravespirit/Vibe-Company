# 技巧库拓展方法论：从 19 到 N

## 一、现有 19 技巧的覆盖地图与盲区

先看清楚现有技巧到底覆盖了什么，才能知道该往哪扩。

### 现有 4 大类的本质

```
T01-T05  Prompt Design     → 解决"怎么说"     → 人→AI 的沟通效率
T06-T10  Iteration Strategy → 解决"何时做什么"  → 过程节奏控制
T11-T15  Thinking Methods   → 解决"怎么想"     → 认知质量提升
T16-T19  Quality Control    → 解决"怎么验"     → 输出可靠性保障
```

### 六个显著盲区

| # | 盲区 | 具体表现 | 为什么现有技巧覆盖不了 |
|---|------|---------|---------------------|
| G1 | **协作与委托** | 多人参与、角色分工、AI 作为团队成员 | 19 技巧全部假设单人对单 AI，没有"怎么把 AI 工作交给别人审"或"多 AI 分工" |
| G2 | **跨会话记忆** | 项目跨天/跨周，上下文断裂 | T18 只解决会话内追踪，没有"怎么在新会话中恢复上下文"的方法 |
| G3 | **多模态协同** | 文本+图表+代码+数据混合迭代 | 技巧都以文本文档为假设，没有"图和文怎么同步迭代"的节奏 |
| G4 | **情绪与认知管理** | 沉没成本、决策疲劳、过度自信 | T14 说"选择不接受"，但没解决"为什么人会倾向接受"的心理根源 |
| G5 | **AI 能力边界感知** | 不知道 AI 擅长什么、不擅长什么 | 没有技巧教用户"在哪些环节应该信任 AI，在哪些环节必须自己判断" |
| G6 | **复用与模板化** | 同类型项目重复造轮子 | T10 只讲单项目内的制度化，没有"跨项目复用迭代模式"的方法 |

## 二、三种拓展路径

拓展技巧库不是随便加——每个新技巧都增加用户的认知负担。三种路径各有适用场景：

### 路径 A：盲区填补（Gap Filling）

**思路**：针对上面 6 个盲区，每个盲区提炼 2-3 个技巧。

**优势**：直接解决用户遇到但现有库无法处理的问题。
**风险**：新技巧可能使用频率低（如 G1 协作场景并非所有用户都涉及）。

**候选技巧预览**：

| 盲区 | 候选技巧 | 核心动作 |
|------|---------|---------|
| G1 协作 | T20 · Delegation Prompt（委托指令） | 写一个"任务简报"让别人（或另一个 AI 会话）能接手你的工作 |
| G1 协作 | T21 · Review Protocol（审阅协议） | 让 AI 以特定角色（CTO / 用户 / 投资人）审阅，模拟团队 review |
| G2 记忆 | T22 · Session Handoff（会话交接） | 每次会话结束前生成"状态快照"：当前版本 + 未决问题 + 下次首要任务 |
| G2 记忆 | T23 · Context Compression（上下文压缩） | 将长对话压缩为结构化摘要，新会话时作为系统提示注入 |
| G3 多模态 | T24 · Modal Sync（模态同步） | 文本改了→检查图表是否需要更新；数据变了→检查结论是否需要修正 |
| G4 认知 | T25 · Sunk Cost Checkpoint（沉没成本检查点） | 每 5 个版本主动问自己："如果我今天第一次看到这个项目，我还会选择当前方向吗？" |
| G4 认知 | T26 · Decision Fatigue Reset（决策疲劳重置） | 感觉"怎么选都行"时，停下来，缩小选择范围到 2 个，用 T11 做最终决策 |
| G5 边界 | T27 · AI Strength Mapping（AI 能力边界地图） | 明确标记"这个环节让 AI 主导" vs "这个环节我自己判断，AI 只提供素材" |
| G6 复用 | T28 · Pattern Extraction（模式提取） | 项目结束后，提取可复用的迭代模式："下次做类似项目，前 3 步应该是…" |
| G6 复用 | T29 · Prompt Library（提示词库） | 将本项目中效果最好的 prompt 保存为模板，标注适用场景 |

### 路径 B：跨领域移植（Cross-Domain Import）

**思路**：从成熟方法论中提取与 AI 协作兼容的技巧。

**优势**：利用已被验证的方法论，不需要从零发明。
**风险**：移植时可能水土不服，需要适配 AI 协作的特殊性。

**来源方法论与可移植技巧**：

| 来源 | 核心理念 | 可移植为 |
|------|---------|---------|
| **设计思维（Design Thinking）** | 同理心 → 定义 → 创意 → 原型 → 测试 | T-Proto · 最小原型测试——先让 AI 做一个最小可用版本，快速验证方向对不对，再扩展 |
| **精益创业（Lean Startup）** | 构建 → 测量 → 学习 | T-MVP · 最小可行版本——每个迭代只做到"刚好能验证核心假设"，不多做 |
| **OODA 循环（军事决策）** | 观察 → 定向 → 决策 → 行动 | T-Tempo · 决策节奏控制——在快节奏环境中，有意识地控制"收集信息"和"做决定"的时间比例 |
| **科学方法** | 假设 → 实验 → 观察 → 修正 | T-Hypothesis · 假设驱动迭代——每个版本明确声明"本版验证的核心假设是 X"，迭代结束时检验 |
| **敏捷开发（Agile）** | Sprint → Retro → Adapt | T-Retro · 迭代回顾——不是评分（那是 Mode 1 Review），而是快速回答三个问题：什么做对了 / 什么做错了 / 下次改什么 |
| **认知行为疗法（CBT）** | 识别自动思维 → 挑战 → 替换 | T-Cognitive · 认知偏误检查——"我是不是因为沉没成本在坚持？是不是因为锚定效应在低估其他方案？" |
| **丰田生产方式** | 5 Why / 现地现物 | T-5Why · 根因追问——当 AI 输出不满意时，不直接改，先连问 5 个"为什么会这样"找到根因 |
| **即兴喜剧（Improv）** | Yes, And... | T-YesAnd · 接纳并叠加——先无条件接受 AI 的创意输出，在此基础上叠加自己的想法，而不是立刻否定 |

### 路径 C：元技巧升级（Meta-Technique Evolution）

**思路**：不新增技巧数量，而是在现有技巧之上构建"组合技"和"升级版"。

**优势**：不增加用户记忆负担，只增加深度。
**风险**：对用户的技巧熟练度要求高。

**组合技与升级版**：

| 名称 | 组成 | 效果 |
|------|------|------|
| **Deep Critique Protocol** | T06 + T11 + T12 + T09 | 四层递进批评：自我攻击 → 多角度分析 → 盲区扫描 → 外部对标 |
| **Paradigm Shift Sequence** | T08 + Navigate(A1-A5) + T14 + T01 | 完整范式跳跃：识别需要跳跃 → 生成方向 → 选择 → 用范式指令重建 |
| **Delivery Pipeline** | T16 + T17 + T19 + T05 | 完整交付流程：验证 → 同步 → 评分 → 格式化 |
| **Diverge-Converge Cycle** | T07(expand) + T11 + T14 + T07(contract) + T10 | 完整发散-收敛：扩展 → 多角度 → 选择 → 收缩 → 制度化 |
| **T01 Pro · Layered Paradigm** | T01 升级 | 不只一个范式句，而是三层：核心原则 → 结构规则 → 边界约束 |
| **T06 Pro · Adversarial Pair** | T06 升级 | 两个 AI 角色——一个攻击，一个辩护，用户做法官 |
| **T14 Pro · Decision Matrix** | T14 升级 | 不只"选 B 因为…"，而是用决策矩阵（维度×权重×评分）量化选择 |

## 三、拓展策略选择矩阵

不同情况下应该选不同路径：

| 你的情况 | 推荐路径 | 理由 |
|---------|---------|------|
| "用户经常遇到19个技巧解决不了的问题" | 路径 A（盲区填补） | 直接堵住功能缺口 |
| "用户觉得技巧太多记不住" | 路径 C（元技巧升级） | 不加新编号，只加组合 |
| "想让技巧库更有理论深度" | 路径 B（跨领域移植） | 站在巨人肩膀上 |
| "想全面升级，做大版本" | A + B 混合 | 先填盲区，再用跨领域丰富 |
| "想小步快跑，低风险试水" | 路径 C 优先 | 零新增编号，只重组现有 |

## 四、推荐的具体行动方案

综合考虑"覆盖面 × 用户认知负担 × 实施难度"，推荐分两期执行：

### 第一期：轻量扩展（T20-T25 + 3 组合技）

目标：覆盖最痛的盲区 + 给高阶用户组合技。

```
新增编号技巧（6 个）：
├── T20 · Delegation Prompt（委托指令）         ← G1 协作
├── T21 · Review Protocol（角色审阅）           ← G1 协作
├── T22 · Session Handoff（会话交接）           ← G2 记忆
├── T23 · Context Compression（上下文压缩）     ← G2 记忆
├── T24 · Modal Sync（模态同步）               ← G3 多模态
├── T25 · Sunk Cost Checkpoint（沉没成本检查点）← G4 认知

新增组合技（3 个，不占编号）：
├── Deep Critique Protocol   = T06 + T11 + T12 + T09
├── Paradigm Shift Sequence  = T08 + Navigate + T14 + T01
└── Delivery Pipeline        = T16 + T17 + T19 + T05
```

技巧总数：25 个编号 + 3 组合技
分类结构：原 4 大类 + 新增"协同扩展（T20-T25）"第 5 类

### 第二期：深度扩展（T26-T29 + 跨领域移植 3-5 个）

前提：第一期上线后收集用户反馈，验证哪些盲区确实存在。

```
新增编号技巧（4 个）：
├── T26 · Decision Fatigue Reset（决策疲劳重置）← G4 认知
├── T27 · AI Strength Mapping（AI 能力边界图）  ← G5 边界
├── T28 · Pattern Extraction（模式提取）        ← G6 复用
├── T29 · Prompt Library（提示词库）            ← G6 复用

跨领域移植（按反馈选 3-5 个）：
├── T-Hypothesis · 假设驱动迭代   ← 科学方法
├── T-MVP · 最小可行版本         ← 精益创业
├── T-5Why · 根因追问            ← 丰田方式
├── T-Retro · 迭代回顾           ← 敏捷开发
└── T-YesAnd · 接纳并叠加        ← 即兴喜剧
```

最终技巧总数目标：~30 个编号 + 5-7 组合技

## 五、质量门槛：新技巧入库标准

不是所有候选都应该入库。每个新技巧必须通过以下检验：

**必过 3 关**：

1. **独立性检验**：它做的事情，现有 19 个技巧（包括组合）真的做不到吗？如果 T06+T11 组合就能解决，就不需要一个新编号。

2. **频率检验**：在 10 个不同类型的项目中，至少 5 个会用到它吗？如果只在极端边缘场景有用，降级为"高级技巧"而非标准库成员。

3. **可执行性检验**：用户读完描述后，能否在 60 秒内开始执行？如果需要 10 分钟理解才能用，说明抽象层次不对。

**加分项**：

- 它有清晰的反模式（anti-pattern）——不只说"该做什么"，还说"不该做什么"
- 它与至少 2 个现有技巧形成有意义的组合
- 它在 Mode 5（Toolkit）的症状映射中能解决至少 1 个目前无法覆盖的症状

## 六、对 Skill 架构的影响

如果技巧库扩展到 25-30 个，现有架构需要以下调整：

| 组件 | 当前状态 | 需要的变化 |
|------|---------|-----------|
| `SKILL.md` | 列出 19 技巧快速索引 | 改为分层：核心 19 + 扩展 6-11，快速索引只显示核心 |
| `references/techniques.md` | 一个文件装所有技巧 | 拆为 `techniques-core.md` + `techniques-extended.md` |
| `references/technique-finder.md` | 12 个症状映射到 19 技巧 | 新增 4-6 个症状模式，映射新增技巧 |
| `references/scene-mapping.md` | 12 场景 × 19 技巧 | 增加新场景列或在推荐中纳入新技巧 |
| `references/evaluation-framework.md` | 6 维度 | 考虑增加 D7（协同效率）或在现有维度中纳入新技巧的评估标准 |
| Mode 5 Toolkit | 12 症状 | 新增症状：S13 跨会话丢失、S14 多人协作混乱、S15 AI 能力误判 |
| 组合技 | 5 个 combo pattern | 新增 3-5 个基于扩展技巧的组合 |

**关键设计决策**：扩展技巧是"平级新增"还是"分层嵌套"？

```
方案 A：平级新增（T20-T30 和 T01-T19 同级）
├── 优势：简单，无歧义
├── 风险：列表越来越长，用户记忆负担增加
└── 适合：技巧总数 ≤ 25

方案 B：分层嵌套（核心层 + 扩展层）
├── 优势：核心技巧保持精简，高阶用户自行探索扩展层
├── 风险：增加理解复杂度（"我该看核心还是扩展？"）
└── 适合：技巧总数 > 25
```

推荐：第一期（25 个）用方案 A，第二期（30+）切换为方案 B。
