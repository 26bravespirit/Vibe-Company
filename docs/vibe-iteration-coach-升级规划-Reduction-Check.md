# Mode 6: ✂️ Reduction Check — 过饱和检测与第一性原理回归

## 设计背景

在复杂的多轮AI迭代中，产出物会不可避免地累积复杂度——每一轮迭代都在"加东西"：新概念、新层级、新规则、新例外处理、新维度。这种膨胀往往不被注意，因为每一个单独的添加在当时都显得合理。

**过饱和的典型表现：**
- 框架层级超过3层，读者需要"学习系统"才能使用系统
- 概念密度过高——一页中出现10+专有术语
- 规则之间出现矛盾或需要"元规则"来仲裁规则冲突
- 异常处理比核心逻辑还复杂
- 支撑材料（附录、解释、示例）超过主体内容
- "这个设计很完美但没人能执行"

**核心洞察：** 过饱和不是"细节太多"的问题，而是"偏离第一性原理"的问题。如果每个设计细节都直接服务于第一性原理，再多也不嫌多。如果设计细节是为了"解决其他设计细节引发的问题"，那就是过饱和。

## 设计定位

### 与现有Modes的关系

```
Mode 6 (Reduction Check) 的定位：

    🧭 Navigate (Mode 4)
         │
         ▼
    📐 Plan (Mode 2)
         │
         ▼
    ⚡ Assist (Mode 3)  ←→  🧰 Toolkit (Mode 5)
         │                        ↕
         │               ✂️ Reduction Check (Mode 6)
         │               (在任意迭代节点可调用)
         │
         ▼
    🔍 Review (Mode 1)
```

**与 Mode 5 Toolkit 的区别：**
- Toolkit 回答 "用哪个技巧"（What tool to use）
- Reduction Check 回答 "是否已经过度了"（Should I stop adding）
- Toolkit 是处方——给你工具去做事
- Reduction Check 是体检——告诉你该不该做

**与 T07 Expand-Contract 的区别：**
- T07 是一种迭代节奏技巧，建议"先扩后缩"
- Mode 6 是一个系统性评估工具，量化回答"缩到哪里、为什么缩"

**与 T25 Sunk Cost Checkpoint 的区别：**
- T25 问 "如果今天重新开始，还会选这个方向吗"（方向层面）
- Mode 6 问 "当前产出物中，哪些设计细节偏离了第一性原理"（细节层面）

## 饱和度评分框架（Saturation Scoring Framework）

### 核心理念

评分基于一个简单判断：**这个设计元素离第一性原理有多远？**

把每个设计元素想象成一棵树上的节点：
- **树根** = 第一性原理（项目存在的根本原因）
- **主干** = 核心机制（直接实现第一性原理的结构）
- **枝干** = 支撑逻辑（为核心机制服务的配套设计）
- **叶片** = 细节规则（具体的操作指引和例外处理）
- **寄生** = 为解决设计缺陷而生的补丁设计

离根越远，饱和度风险越高。

### 第一步：锚定第一性原理

在评估之前，必须先帮用户明确项目的第一性原理。使用以下模板：

```
项目的第一性原理锚点：
├── 核心问题：这个项目要解决什么根本问题？
├── 核心用户：谁是第一优先级使用者？
├── 核心约束：如果只能保留一个规则，保留哪个？
└── 成功标准：怎样算"成了"？（一句话）
```

如果用户无法用一句话说清每一项，这本身就是过饱和的信号。

### 第二步：逐元素饱和度评分

对产出物中的每个可识别的"设计元素"（一个概念、一条规则、一个层级、一个流程步骤、一个评分维度……）进行评分。

#### 距离层级（Distance Tier）

| 层级 | 定义 | 基础分 | 说明 |
|------|------|--------|------|
| **L0 根** | 第一性原理本身 | 0 | 不参与评分，是锚点 |
| **L1 主干** | 直接实现第一性原理的核心机制 | +1 | 必须存在，删掉则系统崩溃 |
| **L2 枝干** | 为核心机制提供支撑的配套设计 | +2 | 重要但可替代，有其他方式实现 |
| **L3 叶片** | 具体操作规则、示例、例外处理 | +4 | 锦上添花，删掉不影响核心功能 |
| **L4 寄生** | 为修复其他设计元素的缺陷而存在 | +8 | 这是过饱和的直接证据 |

#### 调节因子（Modifiers）

在基础分之上，叠加以下调节因子：

**惩罚因子（加分 = 更饱和 = 更危险）：**

| 因子 | 条件 | 惩罚值 | 解释 |
|------|------|--------|------|
| **P1 循环依赖** | 该元素与另一个非L1元素互相依赖 | +3 | 说明设计产生了自我引用的复杂度 |
| **P2 专有术语** | 引入了需要额外解释的新概念 | +2 | 每个新概念都是读者的认知负担 |
| **P3 例外处理** | 该元素是某条规则的例外情况 | +2 | 例外越多，规则越脆弱 |
| **P4 嵌套条件** | 包含 "如果...但如果...除非..." | +3 | 嵌套条件是复杂度的最可靠指标 |
| **P5 解释成本** | 需要超过2句话向新人解释 | +1 | 如果解释不清，可能不该存在 |
| **P6 孤岛元素** | 该元素与系统中其他部分没有明确关联 | +2 | 可能是迭代残留，忘记删除 |

**奖励因子（减分 = 更简约 = 更健康）：**

| 因子 | 条件 | 奖励值 | 解释 |
|------|------|--------|------|
| **B1 直觉可用** | 不需要查文档就能理解和使用 | -2 | 简单到不需要说明书 |
| **B2 即时可验** | 可以在30秒内检验该元素是否生效 | -2 | 短反馈循环 = 高实用性 |
| **B3 单一职责** | 该元素只做一件事，做得很清楚 | -1 | 职责清晰 = 低耦合 |
| **B4 可删除性** | 删除后系统仍然运转，只是稍弱 | -1 | 优雅退化 = 设计健壮 |
| **B5 复用性** | 在多个场景中被引用，而非一次性使用 | -1 | 被多次引用说明确有价值 |

#### 单元素得分公式

```
元素饱和度 = 距离层级基础分 + Σ(惩罚因子) - Σ(奖励因子)
```

- **得分 ≤ 2：** 🟢 健康 — 这个元素有存在的充分理由
- **得分 3-5：** 🟡 注意 — 需要审视是否值得保留
- **得分 6-8：** 🟠 警告 — 强烈建议简化或删除
- **得分 ≥ 9：** 🔴 过饱和 — 应该立即删除或彻底重构

### 第三步：系统级饱和度仪表盘

逐元素评分后，汇总为系统级指标：

#### 3a. 饱和度分布图

```
🟢 健康 (≤2)：  ████████████  12个 (48%)
🟡 注意 (3-5)：  ██████       6个  (24%)
🟠 警告 (6-8)：  ████         4个  (16%)
🔴 过饱和 (≥9)：██           3个  (12%)
```

#### 3b. 系统饱和度指数（Saturation Index）

```
饱和度指数 = (🟠警告数 × 2 + 🔴过饱和数 × 5) / 总元素数 × 100
```

| 指数范围 | 状态 | 建议行动 |
|----------|------|----------|
| 0-15 | ✅ 精简 | 系统健康，继续迭代 |
| 16-30 | ⚠️ 轻度膨胀 | 在下一轮迭代中安排一次收缩（T07） |
| 31-50 | 🔶 中度过饱和 | 暂停新增功能，专门做一轮精简迭代 |
| 51-75 | 🔴 重度过饱和 | 回到第一性原理，用 T01 重写核心框架 |
| >75 | ⛔ 系统性危机 | 建议 T08 版本跳跃 — 从零重建 |

#### 3c. 层级分布健康度

一个健康系统的层级分布应该呈金字塔形：

```
理想分布：           当前分布（示例）：
L1 ████ (20-30%)    L1 ██ (10%)        ← L1太少：核心不清晰
L2 ██████ (30-40%)  L2 ████ (20%)      ← L2偏少
L3 ████ (20-30%)    L3 ████████ (40%)  ← L3过多：细节膨胀
L4 █ (0-10%)        L4 ██████ (30%)    ← L4严重过多：补丁驱动
```

**判断规则：**
- L4 占比 > 15%：过饱和确认——大量设计是在"修复设计"
- L3 占比 > L1+L2 总和：细节膨胀——规则比结构还多
- L1 占比 < 15%：核心稀释——第一性原理在细节中丢失了

## 执行流程

### 调用方式

**触发短语：** "检查过饱和", "是不是过度设计了", "reduction check", "需要减法吗", "complexity check", "这个版本是不是太复杂了", "帮我做个减法", "saturation check"

### 执行步骤

```
Step 1: 锚定
├── 帮用户明确第一性原理（如果用户无法一句话描述，先协助提炼）
├── 确认核心用户和成功标准
└── 输出：第一性原理锚点卡片

Step 2: 扫描
├── 遍历产出物，识别所有可评分的设计元素
├── 对每个元素判定距离层级（L0-L4）
└── 输出：元素清单 + 层级标注

Step 3: 评分
├── 对每个非L0/L1元素进行惩罚/奖励因子评估
├── 计算单元素饱和度得分
└── 输出：逐元素评分表

Step 4: 诊断
├── 生成饱和度分布图
├── 计算系统饱和度指数
├── 分析层级分布健康度
└── 输出：系统级仪表盘

Step 5: 处方
├── 对🟠和🔴元素，给出具体处置建议：
│   ├── 删除 — 该元素不需要存在
│   ├── 合并 — 与其他元素合并可消除冗余
│   ├── 降级 — 从规则变为建议/附注
│   └── 重构 — 该元素本身有价值但实现方式过于复杂
├── 对L4（寄生）元素，追溯它修复的是哪个上游缺陷
│   → 修复上游缺陷而非继续打补丁
└── 输出：处方清单 + 预期简化后的饱和度指数
```

## 关键设计原则

1. **锚定先行。** 不锚定第一性原理就评分，等于没有坐标系的测量。锚定本身可能就需要一轮对话。

2. **不追求零饱和。** 目标不是把所有东西砍到L1。L2和L3元素在合理范围内是健康的。只有L4（寄生设计）和高分🟠🔴是需要行动的。

3. **量化驱动，不靠感觉。** "感觉太复杂了"不可操作。"饱和度指数42，其中3个L4元素贡献了60%的分数"才可操作。

4. **修上游，不打补丁。** 对L4元素，核心行动不是删除L4本身，而是找到它修复的L2/L3缺陷并修复源头。

5. **处方必须具体。** 不是"建议简化"——而是"将规则A和规则B合并为一条，删除例外条款C，将流程D从必须变为可选"。

6. **可重复调用。** 每次精简后可以再跑一次 Reduction Check，验证饱和度指数是否真的下降了。形成"检查→精简→再检查"的循环。

## 与现有技巧的协同

| 场景 | Reduction Check 的角色 | 推荐搭配 |
|------|----------------------|----------|
| 刚完成一轮 T07 Expand（扩张） | 在 Contract 之前先跑 Reduction Check，让缩减有数据依据 | T07 → Mode 6 → 执行缩减 |
| T06 Evaluate-Improve 之后 | 评估报告可能建议加东西，先检查是否已经过饱和 | T06 → Mode 6 → 决定加还是减 |
| T08 Version Leap 之前 | 检查当前版本的饱和度，如果指数 >50，支持跳跃决定 | Mode 6 → T08（如果确认过饱和） |
| T10 Converge to Institution 之前 | 制度化之前必须减法，否则制度文件会过于冗长 | Mode 6 → T10 |
| T16 Verify Before Deliver 中 | Reduction Check 可以作为 T16 验证的子项 | T16 包含 Mode 6 作为检查项 |
| T25 Sunk Cost Checkpoint 之后 | T25判断方向对不对，Mode 6判断细节多不多，互补 | T25（方向）→ Mode 6（细节） |
