# Vibe Iteration Coach 升级规划：大版本迭代方向引导功能

## 一、问题诊断：现有 Skill 缺什么？

当前 skill 有三个模式——Review（回顾评分）、Plan（规划路径）、Assist（实时辅助），覆盖了"怎么迭代"的问题。但在实际使用中，用户最常卡住的地方不是"怎么迭代"，而是**"下一个大版本往哪走"**。

具体来说，当用户完成 v3、v4 这样的版本后，面临的核心困惑是：

- 当前版本已经"够用"了，但感觉还能更好，不知道突破口在哪
- 有很多可能的改进方向，不知道哪个投入产出比最高
- 想做范式跳跃（T08），但跳不出当前思维框架
- 需要有人帮 ta "打开脑洞"，同时也需要有人帮 ta "回到本质"

现有的 T08（Version Leaps）和 T11（Three-Perspective Analysis）提供了方法论指导，但**不生成具体方向**。这正是新功能要填补的空白。

---

## 二、功能定义：Mode 4 · 🧭 Navigate — "下一版往哪走？"

### 触发条件

用户表达以下意图时激活：

- "下一个版本应该怎么改？"
- "我的 v3 做完了，接下来怎么突破？"
- "给我一些迭代方向"
- "这个项目还能往哪些方向发展？"
- "我感觉卡住了，需要新思路"
- "help me find the next version direction"
- "what should v4 look like?"

### 核心输出

基于用户当前版本的内容，生成 **10 个大版本迭代方向**，分两组呈现：

| 组别 | 思维引擎 | 数量 | 特征 |
|------|----------|------|------|
| A 组 | 第一性原理 | 5 个 | 从本质出发，追问"这件事的根本目的是什么"，拆解到最底层再重建 |
| B 组 | 创意驱动 | 5 个 | 从类比、跨界、极端假设出发，寻找非线性突破口 |

用户从 10 个方向中选择 1-2 个（运用 T14 Choose Don't Accept），作为下一个大版本的核心方向。

---

## 三、两组方向的生成逻辑

### A 组：第一性原理方向（5 个）

第一性原理的核心是"剥离所有既有假设，回到最基础的事实和约束，从零开始推导"。生成逻辑如下：

**A1 · 目的回溯（Purpose Regression）**
追问"这个项目最终要解决什么问题？"，检查当前版本是否在解决真正的问题，还是在解决"问题的症状"。如果发现偏移，方向就是回归核心目的。

**A2 · 约束重审（Constraint Reexamination）**
列出当前版本隐含的所有假设和约束条件，逐一追问"这个约束真的存在吗？"。移除虚假约束后，可能打开全新的解空间。

**A3 · 结构简化（Structural Simplification）**
检查当前版本的复杂度是否有"过度设计"的成分。方向是用更少的概念、更简洁的结构达到同等（或更好）的效果。

**A4 · 价值链聚焦（Value Chain Focus）**
分析当前版本中哪些部分真正创造核心价值，哪些是附属。方向是砍掉附属部分，将资源集中到价值链的关键节点上。

**A5 · 终局倒推（End-State Backcast）**
假设项目在 3-5 年后处于最理想状态，那时它长什么样？从终局状态往回推，找到当前版本到终局之间缺失的关键跳跃。

### B 组：创意驱动方向（5 个）

创意驱动的核心是"打破常规思维路径，从意想不到的角度发现可能性"。生成逻辑如下：

**B1 · 跨界移植（Cross-Domain Transplant）**
从完全不同的领域（游戏、生物学、城市规划、音乐……）借鉴一个核心机制，移植到当前项目中。检验这种移植是否能解决当前版本未能解决的问题。

**B2 · 极端假设（Extreme Hypothesis）**
设定一个极端条件——"如果规模扩大 100 倍怎么办？" "如果核心资源为零怎么办？" "如果目标用户完全反转怎么办？"——用极端条件暴露当前设计的脆弱点，并从中提炼出稳健化方向。

**B3 · 用户视角翻转（Perspective Flip）**
站在完全不同的利益相关方视角重新审视项目——最讨厌这个项目的人会怎么看？5 岁小孩会怎么理解？竞争对手会怎么抄？从翻转视角中发现盲区。

**B4 · 反向构建（Inversion Design）**
不问"怎么让它更好"，而问"怎么确保它一定失败？"列出所有能让项目失败的因素，然后逐一取反，得到被忽略的改进方向。

**B5 · 组合创新（Combinatorial Innovation）**
取当前项目中 2-3 个独立模块，尝试意想不到的组合方式。或者引入一个外部元素（AI、社区、游戏化、订阅制……），看与现有模块组合后是否产生 1+1>2 的效果。

## 四、工作流程设计

### Step 1：理解当前版本（Input）

Coach 需要获取以下信息：

```
必要信息：
├── 项目类型（匹配 scene-mapping.md）
├── 当前版本号和核心内容摘要
├── 用户对当前版本的自评（满意什么 / 不满意什么）
└── 用户的模糊意向（如果有的话）

可选信息：
├── 版本演进历史（v1→v2→v3 各做了什么改变）
├── 之前放弃的方向（和放弃的原因）
└── 外部约束（时间、资源、利益相关方）
```

### Step 2：双引擎生成（Process）

```
                    ┌─────────────────────────┐
                    │   用户当前版本 + 上下文    │
                    └────────────┬────────────┘
                                 │
                    ┌────────────┴────────────┐
                    │                         │
           ┌───────▼───────┐        ┌────────▼────────┐
           │  第一性原理引擎  │        │   创意驱动引擎    │
           │               │        │                 │
           │ A1 目的回溯    │        │ B1 跨界移植      │
           │ A2 约束重审    │        │ B2 极端假设      │
           │ A3 结构简化    │        │ B3 视角翻转      │
           │ A4 价值链聚焦  │        │ B4 反向构建      │
           │ A5 终局倒推    │        │ B5 组合创新      │
           └───────┬───────┘        └────────┬────────┘
                   │                         │
                   └────────────┬────────────┘
                                │
                   ┌────────────▼────────────┐
                   │  10 个方向 · 供用户选择    │
                   └────────────┬────────────┘
                                │
                   ┌────────────▼────────────┐
                   │  用户选择 1-2 个 (T14)    │
                   └────────────┬────────────┘
                                │
                   ┌────────────▼────────────┐
                   │  转入 Mode 2 (Plan) 规划  │
                   └─────────────────────────┘
```

### Step 3：结构化输出（Output）

每个方向的输出格式：

```
[编号] 方向名称（英文名）
━━━━━━━━━━━━━━━━━━━━━━━━━━
核心洞察：一句话说明为什么这个方向值得考虑
具体做法：2-3 个 bullet 描述如果选这个方向，下一版会怎么改
预期效果：选择这个方向后，项目会发生什么变化
风险提示：这个方向的主要风险是什么
难度评估：⭐~⭐⭐⭐⭐⭐（实施复杂度）
突破潜力：🔥~🔥🔥🔥🔥🔥（范式跳跃可能性）
```

### Step 4：引导选择与衔接

用户选择后，Coach 应：

1. 确认选择并追问选择理由（强化 T14）
2. 如果选了多个方向，帮助判断是串行还是并行
3. 自动衔接到 Mode 2（Plan），用选定方向生成迭代路线图
4. 在后续 Mode 3（Assist）中持续对照选定方向，防止偏离

## 五、与现有架构的集成点

### 5.1 与现有三个 Mode 的关系

```
用户旅程：
                                    ┌──────────┐
                                    │ Mode 4   │
                                    │ Navigate │ ← 新增
                                    │ 往哪走？  │
                                    └────┬─────┘
                                         │ 选定方向
                                         ▼
┌──────────┐    ┌──────────┐    ┌──────────┐
│ Mode 2   │───▶│ Mode 3   │───▶│ Mode 1   │
│ Plan     │    │ Assist   │    │ Review   │
│ 怎么走？  │    │ 走到哪了？ │    │ 走得好吗？│
└──────────┘    └──────────┘    └──────────┘
       ▲                              │
       └──────────────────────────────┘
              发现需要改方向时，回到 Mode 4
```

### 5.2 与 19 个技巧的关系

| 技巧 | 在 Mode 4 中的角色 |
|------|-------------------|
| T08 Version Leaps | Mode 4 的理论基础——Navigate 本质上是帮用户执行 T08 |
| T11 Three-Perspective | A 组和 B 组就是两种"视角"，比原来的三视角更具体 |
| T14 Choose Don't Accept | 用户从 10 个方向中做出明确选择是 T14 的核心实践 |
| T09 External Benchmarking | A 组的"约束重审"和 B 组的"跨界移植"都隐含外部对标 |
| T12 Blind Spot Discovery | B 组的"视角翻转"和"反向构建"本质是系统化的盲区发现 |

### 5.3 与评估框架的关系

Mode 4 主要影响以下维度的得分：

- **D2 迭代节奏**：在正确的时机启动 Navigate（而非盲目继续微调），本身就是好节奏
- **D3 批判性思维**：10 个方向迫使用户多角度审视项目，避免单一思维惯性
- **D5 主导权**：用户主动选择方向（而非 AI 推荐方向），是主导权的体现

## 七、示例演示

假设用户正在做一个"AI 创业公司组织架构设计"，当前完成了 v3（三层级扁平结构）。

### Navigate 输出示例

**🧭 A 组 · 第一性原理方向**

> **A1 · 目的回溯**
> 核心洞察：v3 在设计"组织结构"，但组织的根本目的是"让正确的信息在正确的时间到达正确的人"。当前结构是否真的优化了信息流，还是只优化了汇报关系？
> 具体做法：重新以信息流为核心变量，画出决策信息的流动路径，找到瓶颈点，围绕信息流而非职级来重构组织。
> 难度：⭐⭐⭐ | 突破潜力：🔥🔥🔥🔥

> **A2 · 约束重审**
> 核心洞察：v3 隐含假设"每个人有且只有一个固定角色"。这个假设在 AI 时代是否仍然成立？当 AI 接管大量执行工作后，人的角色边界是否应该更流动？
> 具体做法：去掉"固定角色"约束，设计一个角色可以动态组合的架构。
> 难度：⭐⭐⭐⭐ | 突破潜力：🔥🔥🔥🔥🔥

> **A3 · 结构简化**
> 核心洞察：v3 有 12 种角色定义，但核心价值创造可能只需要 3 种。复杂度本身是不是在制造沟通成本？
> 具体做法：将角色精简为"创造者 / 连接者 / 守护者"三类，其余全部合并。
> 难度：⭐⭐ | 突破潜力：🔥🔥🔥

> _(A4、A5 类似格式...)_

**🧭 B 组 · 创意驱动方向**

> **B1 · 跨界移植（来源：开源社区）**
> 核心洞察：Linux 内核社区没有"组织架构"，但它协调了上万人的高效协作。核心机制是"代码所有权 + 信任链"而非"汇报关系"。能否将这个机制移植到 AI 创业公司？
> 具体做法：设计基于"项目所有权"而非"部门归属"的协作系统。
> 难度：⭐⭐⭐⭐ | 突破潜力：🔥🔥🔥🔥🔥

> **B4 · 反向构建**
> 核心洞察：如果要让这个组织一定失败，最有效的方法是什么？答案可能是"让决策速度变慢"。那么反过来，v4 的核心设计原则就应该是"最大化决策速度"。
> 具体做法：为每个流程增加"决策延迟"指标，任何增加延迟的结构都需要强理由才能保留。
> 难度：⭐⭐⭐ | 突破潜力：🔥🔥🔥🔥

> _(B2、B3、B5 类似格式...)_

**👉 请从以上 10 个方向中选择 1-2 个作为 v4 的核心方向，并说明选择理由。**

## 八、设计原则与注意事项

1. **方向必须具体，不能泛泛而谈。** "优化用户体验"不是一个方向，"从任务流而非功能模块重组信息架构"才是。每个方向都应该具体到用户能判断"选还是不选"。

2. **两组方向应有张力。** A 组往往导向简化、聚焦、回归本质；B 组往往导向扩展、跨界、打破常规。这种张力是刻意设计的——它迫使用户在"深挖"和"跳出"之间做出有意识的选择。

3. **不替用户做选择。** Coach 可以标注难度和突破潜力，但不应排序或推荐"最佳方向"。选择权必须在用户手中（T14）。

4. **与上下文强关联。** 10 个方向不是通用模板，而是基于用户当前版本的具体内容生成的。同一个项目在 v2 和 v5 时，生成的方向应该完全不同。

5. **无缝衔接后续模式。** 用户选择方向后，应自然流入 Mode 2（Plan）生成实施路线图，而非让用户重新发起一轮对话。
